# 大索引常驻内存优化

2026-10-21（Asia/Shanghai）。在之前的安全与后台占用修复之上继续优化，保留已有改动，未修改磁盘索引格式。优化版已重新构建并正常启动。

## 改动

- 文件完整路径、原始目录路径、小写目录路径的查找表，改为保存 `hash + 索引编号`；真实字符串继续由已有 StringPool 提供。查找始终核对真实路径，哈希相同不会误认成同一个文件。
- 覆盖冷扫描、v5/v6 加载、增删改、WAL 回放、目录前缀重扫和写时复制压缩。路径大小写与去重规则保持原有行为。
- 去掉加载时为所有记录批量构造完整路径的临时字符串数组。
- 构建倒排列表后收紧多余 capacity。列表原本按递增编号构建，无需重复排序。
- 大型数组追加时按约 12.5% 增长，避免加载后的第一次文件事件触发默认倍增；覆盖 StringPool、记录列、路径编号和倒排列表。

没有引入额外依赖，也没有清空用户缓存、缩小扫描范围或关闭搜索功能。

## 同一真实缓存的对照

快照包含 6,424,604 条记录、6,377,185 条有效记录。两个独立构建使用相同缓存及查询；每类查询重复 3 次，随后给内存中的引擎追加 100 条合成记录。合成记录不会写入用户索引或文件系统。原始结果见 comparison-before.txt / comparison-after.txt，快照指纹见 fixture-sha256.txt。

| 阶段 | 优化前内存足迹 | 优化后内存足迹 | 降低 |
|---|---:|---:|---:|
| 查询完成后 | 3712.61 MiB（3.63 GiB） | 2372.72 MiB（2.32 GiB） | 36.1% |
| 追加 100 条记录后 | 4136.66 MiB（4.04 GiB） | 2713.14 MiB（2.65 GiB） | 34.4% |

优化前后按每 1 万条记录抽样，其中有效记录的路径均能正确反查。六类查询返回数量一致；样本查询耗时仍为毫秒级：

| 查询 | 优化前平均 ms | 优化后平均 ms |
|---|---:|---:|
| readme | 2.410 | 0.685 |
| *.swift | 0.161 | 0.178 |
| config | 1.262 | 1.300 |
| /Applications/ | 4.295 | 4.242 |
| size:>1mb | 1.936 | 1.812 |
| type:folder | 6.009 | 5.396 |

这只是小样本回归对比，不足以宣称所有查询更快。此次串行复测中的完整启动时间为 5.87 秒 → 6.18 秒，存在约 0.31 秒的差异。构建和基准工具没有向外发送索引内容。

新进程通过了真实文件创建可搜索、重命名可搜索、旧名消失、删除后结果消失四项验证，见 live-files.json。

## 首次定时写盘观察

日志确认新进程在 16:41:41 完成一次约 708 MiB 的 v6 全量落盘。10 秒间隔采样中，内存足迹从保存前约 2272 MiB 上升到约 3056 MiB，随后在 16:42:25 回落到约 2165 MiB（2.11 GiB），没有停留在写盘时的高位。RSS 同期最高采到约 3627 MiB，之后回落到约 2785 MiB。

这验证了本次观察中的回落行为；10 秒间隔无法捕捉精确瞬时峰值，也不是长时间无泄漏证明。全量快照复制和约 708 MiB 的写放大仍待后续优化。原始序列见 gui-save-cycle.json。
