# 153：索引压缩同时触发时不再误删几乎全部记录

日期：2026-11-09

修复两次 `SearchEngine::compactRecords()` 重叠运行时清空索引的问题。一次线上事故中，存活记录从约 650 万降到 24,741 条，结果随后写入 `index.v6`，重启后仍然保持损坏状态，大部分文件搜索不到。

原因：压缩的第三阶段按快照中的编号比对当前数据，前提是两者的记录和目录编号一致。定时落盘（`IndexPersistence::fullCompact`）和目录重扫后的检查（`ServiceEngine::rescanSubtree`）可以同时进入压缩。第一次压缩换入重新编号的数据后，第二次比对全部失配，把快照里的路径都当成压缩期间被删除并逐条标记墓碑，日志为 `replayed 0 adds, 6472797 deletes`。

- `compactRecords` 增加专用互斥锁并用 `try_to_lock` 获取：已有压缩在运行时，后到的调用直接返回空映射，不会等待，也不会占用第二份快照内存。
- 第三阶段换入数据前校验 `compactionGen_`：如果第二阶段期间 `loadRecords` 等操作整体重新加载过记录，放弃本次压缩，避免用旧快照覆盖新数据。

已损坏的本地索引不会自动恢复，升级后需要执行一次 Rebuild Index。

测试：Part 3d 新增两个并发场景，覆盖同时压缩不丢记录、存活文件仍可按路径找到、墓碑被回收，以及压缩期间重新加载的数据不被覆盖。修复前这些丢失断言失败，只加互斥锁时重新加载场景仍失败，两项修复都加上后通过；Part 3d 连续运行 20 次无失败，`make test-fast` 全部通过（12291 项）。

版本号和构建号未修改（仍为 1.4.0，Build 4）。
